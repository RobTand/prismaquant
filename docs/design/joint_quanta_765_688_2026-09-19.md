# Joint quanta: distributed head-walk verification (#765) and why prepare stays whole-roster (#688)

2026-09-19. Implements the PrismaQuant side of #765; reports the #688 gap
with its join contract. PrismaBuild owns sharding, placement and execution
throughout -- this document names verifiable quanta and coverage proofs and
builds no dispatcher.

## 1. #765: the head-walk verification quantum

The head walk resolves every census unit (identity reads plus wire checksums,
plus proving each cell's render origin) and, since #754, banks each verified
unit under the campaign's own checkpoint machinery with commitment in the
roster's one deterministic order. The walk's read set is the wire corpus the
movers already carry, so under stage-tier residency a fleet-distributed walk
reads staged bytes, not NFS.

### 1.1 The quantum (data)

`prismaquant/joint_head_walk_quanta.py`, stdlib only:

* `head_walk_quanta(names, max_units_per_quantum=...)` cuts `sorted(names)`
  into contiguous half-open `[lo, hi)` descriptors. Each carries its slice,
  the full-roster digest, a slice digest, and the quantum count. Pure data:
  no threads, no placement, no execution.
* `check_quantum_for_roster(quantum, names)` binds one descriptor to the live
  census before it may bank anything. A descriptor from another campaign or
  roster revision refuses here.
* `verify_quanta_coverage(quanta, names)` is the coverage proof: one shared
  roster digest, unique ids, slices tiling `[0, N)` with no gap and no
  overlap. A lost or duplicated quantum is a refusal, never a silent hole.

### 1.2 Banking a slice (opt-in)

`load_measured_anchor_input(..., head_walk_quantum=None)`. Without a
descriptor every refusal and every identity byte is exactly today's: a scoped
read still cannot bank. With one, the caller must also pass the matching
`unit_scope == (lo, hi)` and a `head_checkpoint` shard directory, and the
slice journal is bound to the FULL roster digest plus the descriptor itself
-- never to the slice alone. The walk, the banking cadence, the fence
re-verification and the progress currency are otherwise unchanged, so a
quantum shard is an ordinary head journal over a roster prefix of one slice.

### 1.3 Collector

`join_head_walk_journals(receipts, dest=..., names=...)` takes one
`{quantum, journal_dir}` per quantum plus the full census roster the join must
reproduce -- supplied by the submitter, never derived from the surviving
shards, so a lost quantum fails the coverage proof instead of shrinking the
roster to fit. It:

1. opens each journal strictly (manifest match, per-envelope identity binding
   and payload digest on load) and refuses a receipt retargeted at another
   descriptor;
2. checks custody across journals -- one shared input set, checkpoint seal,
   roster digest and encoder-reuse binding; only the per-quantum marker may
   differ -- and replays the coverage proof over the concatenated slices;
3. re-envelopes the verified unit states under the full-roster identity into
   a fresh `dest`.

The joined journal is indistinguishable from a single-container walk's (same
stage, same identity keys minus the marker, one envelope per unit), and the
existing resume path re-verifies every banked unit against the live bytes
before trusting it. The join is therefore never trusted -- only the coverage
proof has to hold.

### 1.4 Fleet execution (submitter's job, not this PR's)

Each quantum publishes as one `pbcampaign` row -- one action like a movement
node, residency-gated on the stage tier via its data manifest, eligible for
ram promotion, reporting resolved units under its declared progress phase.
The row shape (demand, manifests, container spec) is owed with the submitter;
this PR deliberately stops at the producer/consumer/collector contract so no
application-side dispatcher is built.

### 1.5 Measurement gate (D45)

Fleet execution waits on the campaign's own resubmission saying whether the
walk is checksum-bound or read-bound at full-core fan-out
(`PRISMAQUANT_HEAD_WALK_WORKERS=1` against the affinity default, head-phase
wall time and `/proc/PID/io` either side). A read-bound walk is fed by the
tier rate, not by core count, and distributing it first would only multiply
readers against the same feed. Until that measurement lands this machinery is
opt-in and the production prepare path passes no descriptor.

## 2. #688: why prepare cannot be unit-scoped, and what the join would take

`parse_unit_scope` already cuts `lo:hi` over the one roster order and
`load_measured_anchor_input` already walks a scope -- but only the standalone
`synthesize` stage may use it. `prepare` exposes no scope flag, and
`execute` actively refuses a scoped input
(`tessera_joint_aura.py`, "joint execution requires the complete campaign
roster in its own caches"). That refusal is load-bearing, not missing
plumbing. Three whole-roster objects have no partial grammar:

1. **Journal identity.** `prepare_cache` seals `cell_count` and
   `cells_sha256` over the loaded cells. A scoped row would bank an identity
   naming a partial cell digest that no full-roster `run` replay would match.
2. **Completion.** `PREPARED_SCHEMA` `status: "complete"` carries one
   `measured_cells` count, one `formats_by_qname` map, one `production.pkl`
   written atomically. There is no partial/merge grammar.
3. **Source authentication.** `authenticate_complete_source()` and the sealed
   prewarm/replay frontier are whole-source, whole-roster objects.

Deleting the refusal and adding a flag would therefore publish scoped rows
with non-joinable identities -- the failure the triage verdict on #688
already predicted. The join contract owed before any unit-scoped prepare row
is publishable:

* scope only the qualification walk (the per-unit journal already supports
  disjoint ranges); keep the whole-roster input load;
* compute the journal's cell digest from the census roster, not the loaded
  cells, so scoped rows share one journal identity (a sealed-identity change:
  needs-design, needs-decision, never a silent migration);
* define the completion merge grammar (N partial journals under one shared
  identity, merged by a collector that replays the same coverage proof as
  §1.3) and the per-scope source-auth binding;
* `run`'s replay must accept journals covering an exact partition.

Until that contract is designed, reviewed and sealed, #688's own posture
stands: the gap is reported, not worked around. This PR pins it with the
banking-gate test (scope without a joinable identity still refuses) and
changes no prepare/run behavior.

### 2.1 Disposition, 2026-09-22: the qualification pass fanned out without `prepare`

The GLM-5.3 campaign's largest qualification pass, which #688 named, has
since run as PrismaBuild quanta. It did not go through `prepare`, and
`prepare` still refuses a scoped input.

What ran: 36,288 retained `TESSERA_E2M1_K2_R896` expert cells were
qualified for addition to an already-prepared panel.

* `tools/build_t4_overlay_catalog.py` froze one catalog cell per unit
  (`adopted-catalog.json`, sha256 `71238bda…`). Each cell adopts its
  source, Hessian, projection and calibration commitments by exact equality
  with a cell the panel had already qualified. Nothing is re-encoded.
* `tools/build_t4_logical_request.py` and `tools/build_t4_recovery_request.py`
  describe the cells as one PrismaBuild logical request. PrismaBuild's
  decomposer cut parent `9b42adf78a72` (plan `fad02101e4ad`) into 166
  children. PrismaQuant cut nothing.
* `tools/qualify_t4_overlay.py` is the per-batch adapter. For a new cell,
  under the staged-tier policy (`--allowed-tiers`), it first waits for the
  declared wire and render spans to be staged. It then verifies the wire, decodes it with the installed Tessera decoder, and requires the
  decode to equal the retained render bit for bit. It writes one result file
  per cell, bound to the cell's digest. A result from an earlier partial
  campaign is reused only after its digest and file stamps are checked; the
  recovery proof records 13,799 such reuses.

Evidence: all 166 children executed with rc 0 (110 on sparky, 56 on
sparklina; 5 of them were cache hits for the final campaign). Group receipt
`1e21ba9d492e` merged 36,288 tasks into `ac1bd31c3674`. Every child's
checkout snapshot has parent `5a7dbafb2c`. The log is
`/home/rob/tmp/codex-glm-20260922/t4-remainder-afterdrain-campaign.log`.

How the four steps above map onto this path:

1. Only the qualification walk is scoped. The catalog is the whole roster.
2. The shared identity is the catalog digest, not a journal `cells_sha256`.
   Each result binds its own cell's digest.
3. The merge is `tools/assemble_t4_overlay.py`. It requires a result for
   every catalog cell, checks each against its cell and the file stamps, and
   writes a new plan, `prepared.json` and `production.pkl` under
   `proposed-overlay/`. Source authentication is carried over from the
   original prepared completion, not recomputed. As of 2026-09-22 the
   assembly has not run: no `proposed-overlay/` directory exists.
4. `run` is unchanged. It reads the assembled completion as an ordinary
   whole-roster prepared input.

Scope: this path adds qualified candidate cells whose source and Hessian
commitments already exist in a prepared panel. A from-scratch `prepare` is
still one action, and a unit-scoped `prepare` still owes the four steps
above. RobTand/prismaquant#688 is closed on the narrower reading: the pass it
measured now fans out across both GB10s.

## 3. Capability-gap disposition

* No PrismaBuild subdivision gap was found for either issue: `pbcampaign`
  already publishes independent rows with data manifests, progress phases and
  residency gating. The gaps are PrismaQuant-side -- the #765 submitter row
  shape (§1.4) and the #688 join contract (§2) -- and both are specified
  above rather than built around.
* No new cache, preload, residency or scheduler was added. The walk reads
  through `_read_verified_wire_blob` (stage/ram/pool with digest admission);
  the join copies verified states between journals the existing machinery
  owns.
